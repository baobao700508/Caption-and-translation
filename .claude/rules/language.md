# 文档与对话语言规范

本规范定义了 AI Agent 在开发过程中使用的语言规则。

## 对话语言

**强制要求**：与用户对话时使用中文。

## 文档编写规则

### 主要语言

- **文档内容**：使用中文撰写
- **代码注释**：使用中文撰写

### 例外情况（使用英文）

以下情况必须使用英文：

1. **命名规范**：
   - 变量名（如 `userName`, `isActive`）
   - 函数名（如 `createUser`, `fetchData`）
   - 类名（如 `UserService`, `ApiClient`）
   - 文件名（如 `user-service.ts`, `api-client.ts`）

2. **专有名词**：
   - API、SDK、MCP
   - HTTP、REST、GraphQL
   - React、Next.js、TypeScript
   - Supabase、PostgreSQL

3. **技术术语**：
   - 保持技术术语的标准英文表达
   - 例如：middleware、hook、component、route

4. **代码示例**：
   - 代码中的标识符使用英文
   - 代码块内的注释使用中文

## 表达方式要求

- **优先使用业务性语言**：面向用户汇报、解释方案、说明 bug 或风险时，优先描述功能表现、界面变化、用户操作路径和最终业务结果，而不是先描述函数、变量、分支或状态流转。
- **先讲用户会看到什么**：回答时先说明"这个功能最终会怎么表现""用户实际使用时会遇到什么现象""会带来什么结果或损失"，必要时再补充对应的技术原因。
- **避免只停留在程序性语言**：不要只说"某个函数进入某个分支""某个变量变成某个值""事务不对等导致回滚"；要进一步翻译成业务后果，例如"用户重复提交后会多出一条订单数据"、"页面会显示成功，但后台实际没有保存完整数据"。
- **善于举例**：优先使用具体场景、小例子和类比帮助用户理解，把抽象技术问题解释成可感知的业务问题。
- **采用费曼式表达**：用普通人能听懂的话把复杂问题讲清楚，减少术语堆砌。除非用户明确要求代码级分析，否则不要把回答重心放在实现细节上。

## 示例

### 正确示例

```typescript
// 创建用户服务
export class UserService {
  // 获取用户列表
  async getUserList() {
    // 实现逻辑...
  }
}
```

**文档说明**：本服务用于管理用户数据，提供 CRUD 操作。

### 错误示例

```typescript
// Create user service
export class 用户服务 {
  // Get user list
  async 获取用户列表() {
    // Implementation logic...
  }
}
```

**Documentation**：This service is used to manage user data and provide CRUD operations.

## 总结

- **对话**：中文
- **文档**：中文为主，专有名词和技术术语英文
- **代码**：标识符英文，注释中文
- **命名**：全部英文
- **表达**：优先讲业务表现、用户影响和实际结果，少讲纯实现细节
