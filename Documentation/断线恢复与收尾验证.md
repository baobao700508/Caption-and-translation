# LiveCaption 断线恢复与收尾验证

本报告的基线验收版本为 **0.1.4（build 5）**。当前 **0.1.5（build 6）** 的断线定位、检测方式与译音收尾方案见[断线定位与 JEV 评估](断线定位与JEV评估.md)。双击桌面 `LiveCaption.app` 即可打开；应用启动后等待开始记录。桌面 `LiveCaption配置.json` 继续提供现有服务和字幕重排配置。

Google 收尾误判已修复。翻译线路采用“断线期间明确丢弃，重连后从当前声音继续”的恢复策略，已经用真人录音验证主动断线和自然断线。**本机到北京百炼的 WebRTC 连接仍在测试中发生过失联，不能称为连续无损；已验证的是缺口可对账、恢复后不补传旧声音、不形成持续积压。**

## 修复内容

### Google 正式末段不再被误判为失败

旧实现发送结束输入后固定等两秒，随后直接返回失败；即使 Google 已返回最后一句正式转写，也会写出尾部未完成。停止流程还会先取消发送任务，URLSession 的取消处理可能把 WebSocket 一并关闭，影响后续结束输入事件。

现在正常停止先关闭输入生产、排空发送任务，再发送 `audioStreamEnd`。Google Transcribe 的 `inputTranscription` 是正式结果，`interimInputTranscription` 是临时结果；程序追踪这两者及最后输入版本，最多等待十秒确认末段。仅有临时文字、传输失败或超时仍判为未确认。发送队列排空另有八秒上限，超时记录缺口并关闭连接，不无限等待。

依据是 [Google Live Transcribe 官方说明](https://ai.google.dev/gemini-api/docs/live-api/live-transcribe)：结束输入会推动缓存音频处理及语段定稿。最终转写是输出确认，不能解释为服务器逐采样点接收回执。

### 失联后及时重建，停止沿用旧连接

原生桥接以前只处理 ICE failed。实测先出现 disconnected，再过约十秒才到 failed，应用在这段时间仍继续把音频交给已经失去连通性确认的连接。

现在 disconnected 持续两秒就触发恢复；两秒内恢复正常则取消该次判定。计时器绑定连接状态版本，旧计时器不能误杀后来的连接。已主动结束输入的连接由收尾协议和超时处理，不再被实时重连计时器提前关闭。

重建期间保留“结束记录”操作，暂停模式和音源切换，避免用户切换与后台恢复同时创建连接。恢复结束后重新开放这些设置。

### 缺失音频明确丢弃，后续音频不排长队

发送队列容量仍有上限；每次发送前剔除已排队超过 750 ms 的旧包，单批最多合并 500 ms。重连就绪时记录恢复切点，采集开始早于切点的整包都丢弃，不补传、不插入假静音、不携带旧恢复句柄重放上下文。

`input.discarded` 记录样本数、采集起止时间、原因和 `replayed: false`。队列溢出也保存计数与时间范围，不能只删数据而不记账；统计只保留数字，不建立另一份音频积压。首包新声音成功后，`live.md` 和 `transcript.md` 显示本次丢弃的时长，AI 中途读日志也能看到缺口。

上传 WAV 仍如实保存客户端接受的字节；编码器观察轨按连接代次记录样本偏移和数量，用来核对旧连接尾部与新连接输入。断开前已经交给连接的音频是否到达服务器，客户端不能倒推；不会把这部分声称为“确认收到”。

### 旧译音和迟到结果不污染恢复后的播放

失联立即清空待播放译音，并使旧连接代次失效。旧代次迟到的译音不能进入播放队列；迟到文字保留原日志归属，不覆盖新字幕。旧发送任务晚到的错误，也不能触发对新连接的再次拆除。

改动集中在 Swift 异步任务、连接代次与有界队列，以及原生 WebRTC 的状态回调。模型选择、麦克风处理和系统声音降噪继续使用现有实现。书面同译与同声传译共用这套发送与恢复代码；两者只在输出模态和译音播放上分支。

## 真人录音验证

音源来自 [OpenSLR LibriSpeech test-clean](https://www.openslr.org/12/)，许可 CC BY 4.0。使用 `6930/75918` 同一章节的连续真人朗读：七段共 76.145 秒，十四段共 102.635 秒；另截取前 25 秒用于最终构建的受控断线检查。每个片段按原顺序输入一次，没有合成、循环、加增益或插入静音。来源、参考文本与 PCM 哈希保存在 `TestResults/fixtures/librispeech/provenance*.json`。

文件按真实时间进入实际 AppSession、发送队列、真实云 API、字幕投影、后台重排和运行中日志。测试未开启物理麦克风或扬声器，不代替远场收音和实际扬声器回声验收。

独立原生窗口检查未返回结果，未计入通过项；重连时“可结束、禁止并发切模式”由实际文件输入测试读取应用状态验证，不等于真实鼠标点击验收。

自然断线测试中，旧连接已有 1,280 个样本、约 80 ms 未进入编码器观察轨；最终主动断线测试为 1,760 个样本、约 110 ms。这与上表“尚未提交而明确丢弃”的时段分开统计，不跨连接补传，也不当作服务器收到的证据。

115 ms、110 ms 测的是**采集开始到客户端提交**，包含 100 ms 分包时间，不是模型翻译延迟。自然断线测试恢复后首条原文约 1.871 秒、译文约 1.888 秒；最后一次原文和译文更新分别在文件输入结束后约 1.260 秒、1.487 秒出现。该样本收到约 90.35 秒译音，保存在 `translated.wav`；这些时间不代表整堂课的词级延迟分布。

断过线的整场日志仍保留 `tail_incomplete: true` 和缺口，即使 `connection.final_finish.confirmed: true`。前者保留整场的不完整性，后者只确认最后连接正常结束。主动断线测试的 `success` 表示恢复验收成功，`full_input_success` 仍为 false；不能把故意丢弃的声音算成完整上传。

## 对断连原因的证据边界

多次失败前，ICE 探测请求继续增加，收到的回复计数停止，随后进入 disconnected／failed；同时本机编码器输入继续消费，underflow 为零。失联分别在不同时间出现，不能据此建立“固定第 20 个包必坏”的规则。关闭 App Nap 的对照仍复现，未把阻止 App Nap 作为修复保留。

这些证据将故障定位到 WebRTC 连通性失去确认，不能进一步区分网络路径丢弃、远端不响应或互操作问题，也不能归罪于某个供应商或运营商。没有关闭 ICE 连通性检查来强行显示连接正常。原生协议仍依据 [百炼 WebRTC 接入说明](https://help.aliyun.com/zh/model-studio/realtime-webrtc-access)。

保留的失败记录包括：76 秒录音快结束时自然断线、一次主动断线后又发生第二次自然断线，以及末段没有收到百炼完成事件的运行。它们继续标为失败或未确认；最终成功的恢复检查没有覆盖或删除这些记录。本报告的基线版本解决客户端恢复与积压处理，不承诺消除这条跨地区连接的所有失联。

每份 `result.json` 的 `log_path` 指向课堂事件、运行中 Markdown、上传音频、编码器观察音频与译音。`scripts/analyze-recovery.py <result.json>` 可重新核对每个音频区间、连接切点、样本字节、丢弃数及后续输入时效。

```bash
bash scripts/check.sh
bash scripts/verify-human-app.sh transcribe
bash scripts/verify-human-app.sh subtitles
python3 scripts/prepare-human-fixture.py --utterances 14
LIVECAPTION_HUMAN_FIXTURE="$PWD/TestResults/fixtures/librispeech/human-speech-14.wav" \
  bash scripts/verify-human-app.sh speech
LIVECAPTION_HUMAN_FIXTURE="$PWD/TestResults/fixtures/librispeech/human-speech-25s.wav" \
  bash scripts/verify-human-app.sh speech "$HOME/Desktop/LiveCaption配置.json" \
  --file-disconnect-after 5 --file-reconnect-delay 3.5
```

这些命令会调用配置中的真实云 API，不播放测试音、不录制环境声音。自然断线测试必须结合恢复对账读取，完整上传检查仍会如实报告缺口。
