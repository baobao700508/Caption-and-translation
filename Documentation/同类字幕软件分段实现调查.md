# 同类字幕软件分段实现调查

## 调查范围与结论

本报告核查公开仓库的具体提交及实际调用路径。结论来自静态源码审查；未运行这些应用、下载模型、上传课堂录音或测量它们在本机的真实延迟。README 的功能描述与当前代码不同之处会单独指出。

`LiveCaption`／`LiveCaptions` 并不唯一对应一个开源项目。本报告分别核查 Windows 翻译工具 SakiRinn/LiveCaptions-Translator、macOS 命令行工具 six-ddc/livecaption、Linux 转写工具 abb128/LiveCaptions，以及用户此前提供的 TheDeathDragon/LiveTranslate。

这些实现没有把“语义段落模型”作为必需条件。三个翻译项目先获取原文，再对选定的文字调用翻译；原译配对因此可以绑定到一次翻译任务。规则分句、标点、停顿、长度或时间限制负责组织片段，显示层再管理“正在变化的文字”和“已经提交的历史”。Linux 转写工具则主要做滚动换行。各项目也保留了硬切、截断或丢弃迟到更新的折中，不能直接拿来当作我们的产品标准。

## TheDeathDragon/LiveTranslate

### 分句不是一个统一开关

这个项目有两条行为不同的处理路径。`_incremental_enabled` 初始为 `False`，可在设置中开启。普通路径在音频片段结束后识别，直接把结果作为一个消息显示并翻译；不能把可选增量模式的句子处理描述为所有运行方式都默认具备。[模式状态](https://github.com/TheDeathDragon/LiveTranslate/blob/190ef027f38e577b0d2ecd06058ff6cbd236496b/main.py#L259-L266)、[普通片段路径](https://github.com/TheDeathDragon/LiveTranslate/blob/190ef027f38e577b0d2ecd06058ff6cbd236496b/main.py#L1255-L1307)

增量路径周期性识别尚未结束的音频，调用 `yasbd.pysbd_adapter.Segmenter` 分句。yasbd 是规则式句界库，不是调用大模型理解话题。得到多个句子后，先取 `sentences[:-1]`，保留最后一句等待继续；短到不超过 8 个字母／数字字符的句子暂存在缓冲，随后拼到下一条。另有前后文本重叠去重，防止重复识别造成重复字幕。[分句调用](https://github.com/TheDeathDragon/LiveTranslate/blob/190ef027f38e577b0d2ecd06058ff6cbd236496b/main.py#L1356-L1409)、[保留尾句与提交](https://github.com/TheDeathDragon/LiveTranslate/blob/190ef027f38e577b0d2ecd06058ff6cbd236496b/main.py#L1451-L1525)、[yasbd 项目](https://github.com/speedyk-005/yasbd-lib)

它也有明确的折中：分句后仍只有一个长片段时，会尝试在逗号、分号或顿号处分开；阈值通常为 60 字符，含顿号时为 25 字符。音频达到最大长度还会回找停顿强制切块。VAD 最后释放的剩余文字直接提交，不保证跨两次 VAD 定稿重新合并半句话。因此可以借鉴尾句缓冲，不能称它解决了所有跨片段语义问题。[逗号兜底](https://github.com/TheDeathDragon/LiveTranslate/blob/190ef027f38e577b0d2ecd06058ff6cbd236496b/main.py#L1368-L1386)、[音频长度保护](https://github.com/TheDeathDragon/LiveTranslate/blob/190ef027f38e577b0d2ecd06058ff6cbd236496b/vad_processor.py#L195-L219)、[剩余文字提交](https://github.com/TheDeathDragon/LiveTranslate/blob/190ef027f38e577b0d2ecd06058ff6cbd236496b/main.py#L1578-L1621)

### 显示、翻译与记录

每次提交原文生成 `msg_id`。翻译过程中将累计译文更新回同一个 ID 的 `ChatMessage`，因此不会出现先积累整篇英文、最后再放整篇中文。卡片的原文与译文都允许自然换行；流式译文显示用 50 ms 定时器合并刷新，这个数字是 UI 节流间隔，不是端到端翻译延迟。[翻译更新](https://github.com/TheDeathDragon/LiveTranslate/blob/190ef027f38e577b0d2ecd06058ff6cbd236496b/main.py#L1080-L1101)、[原译卡片与刷新](https://github.com/TheDeathDragon/LiveTranslate/blob/190ef027f38e577b0d2ecd06058ff6cbd236496b/subtitle_overlay.py#L193-L274)

它区分两个显示面：聊天式悬浮窗保留最近 50 条消息并可滚动；独立的精简字幕窗默认保留最近 1 条，可配置数量，按像素宽度和词／标点边界换行、扩展高度。在已检查的这些路径中，没有把每条正文截成尾部几行后要求点击“展开全文”的机制。旧消息离开当前窗口，与在每条消息中隐藏前半段，是不同的产品行为。[消息窗口容量](https://github.com/TheDeathDragon/LiveTranslate/blob/190ef027f38e577b0d2ecd06058ff6cbd236496b/subtitle_overlay.py#L1147-L1184)、[精简窗换行](https://github.com/TheDeathDragon/LiveTranslate/blob/190ef027f38e577b0d2ecd06058ff6cbd236496b/subtitle_window.py#L353-L398)、[精简窗保留条数](https://github.com/TheDeathDragon/LiveTranslate/blob/190ef027f38e577b0d2ecd06058ff6cbd236496b/subtitle_window.py#L853-L865)

启用日志时，原文识别后立即写原文文件，译文完成后按同一 `msg_id` 写译文与双语文件；文件使用行缓冲，适合持续读取。它不等同于我们保存全部 interim／revision 的事件日志，但“屏幕容量有限、文件记录独立持续保存”值得保留。[日志实现](https://github.com/TheDeathDragon/LiveTranslate/blob/190ef027f38e577b0d2ecd06058ff6cbd236496b/transcript_writer.py#L46-L95)

## SakiRinn/LiveCaptions-Translator

### 文字从哪里来

该项目没有自行从声学信号识别句界，而是通过 Windows UI Automation 读取 `CaptionsTextBlock.Current.Name`。因此拿到的是 Windows 字幕窗口中不断变化的文字，底层识别、停顿判断和标点主要来自 Windows。[读取实现](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/src/utils/LiveCaptionsHandler.cs#L84-L97)

### 怎样判断一句以及何时翻译

- 句末集合是 `.?!。？！`。先处理部分英文缩写和标点空格，再找最后一个句末符号，取其后内容作为当前句；若文本末尾已经是句末符号，则回找前一个边界，以保留刚完成的整句。
- 当前尾句少于 **10 个 UTF-8 字节**时，可能并入前一句。它使用的是字节阈值，不是完整语义判断。
- 文本以句末标点结束时立即排队翻译；尚未结束时，累计变化次数超过 `MaxSyncInterval` 或相同文字持续达到 `MaxIdleInterval` 也会触发翻译。默认分别为 **3** 和 **50**；主循环末尾休眠 25 ms，但 UI 读取等操作也耗时，因此不能把 50 轮直接写成精确 1.25 秒延迟。
- 新文字到达会更新当前文字，而不是把每次读到的结果都追加成新段。这里不存在保证“句子语义已经完整”的独立定稿信号。

证据：[当前句提取与触发条件](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/src/Translator.cs#L77-L157)、[默认设置](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/src/models/Setting.cs#L18-L22)、[字符集合与阈值](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/src/utils/TextUtil.cs#L7-L15)。

### 半句、修订与中英配对

每个翻译任务保存提交时的 `OriginalText`；完成后用该快照与译文一起记入历史。新任务先完成时，会取消它前面的旧任务，避免较旧结果后来覆盖最新结果。判断是否覆盖最后一条历史的规则，是取两个原文相同的最短长度、计算前缀相似度，超过 **0.6** 就删除最后一条再写新记录。它可以处理一部分增长或修订，但不能等同于有可靠段落 ID 的修订协议。[任务与取消逻辑](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/src/models/TranslationTaskQueue.cs#L17-L65)、[相似度覆盖条件](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/src/Translator.cs#L345-L357)

当前浮窗的原文和译文是分别绑定、分别更新的。译文显示过去若干条译文加当前译文，原文显示最近范围；不是把每个历史原译对作为独立字幕行逐对插入。历史卡片才是同一记录的 `SourceText` 与 `TranslatedText` 上下排列。故它能证明“翻译任务要保留来源”，不能证明其浮窗已经提供严格同步的一句英文一句中文。[浮窗绑定](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/src/windows/OverlayWindow.xaml#L65-L92)、[历史卡片](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/src/pages/CaptionPage.xaml#L68-L117)

### 截断与日志的实际取舍

它确实存在长句删前缀：主页面的当前原文和译文调用 `ShortenDisplaySentence`，默认 **220 个 UTF-8 字节**，超过后沿标点移除前面的内容。这个函数不是语义分段，也不是用户点击后展开的折叠机制；无可用标点时还可能保留超长文字。不能把这段行为直接搬到要求完整连续阅读的课堂浮窗。[截短函数](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/src/utils/TextUtil.cs#L17-L26)、[原文调用](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/src/Translator.cs#L117-L124)、[译文调用](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/src/Translator.cs#L206-L223)

日志保存于 SQLite `translation_history.db`，字段包括时间、原文、译文、目标语言和 API。写入发生在翻译任务完成之后，修订覆盖会删除上一条；它不是保存全部 interim／revision 的事件日志。[数据库结构与写入](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/src/utils/HistoryLogger.cs#L23-L83)、[覆盖写入](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/src/Translator.cs#L271-L291)

README 所说的悬浮窗句数、历史和 CSV 导出，与这些实现方向一致；“LLM 擅长不完整句子”是项目的使用建议，不是它已经解决半句分段的实测证据。此外，换行预处理会根据 **40 字节**阈值补句号或破折号，进一步说明它包含启发式标点改写，不适合作为忠实记录规则直接复制。[README](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/README_zh-CN.md#L84-L124)、[换行替换](https://github.com/SakiRinn/LiveCaptions-Translator/blob/a6fee12757b15edbeef7c60f8895e0be694801e1/src/utils/TextUtil.cs#L29-L44)

## six-ddc/livecaption

### Nemotron 路线的具体断句规则

它将 Silero VAD 与 ASR 输出标点结合，而不是仅凭一次停顿就立即提交：

| 条件 | 当前源码行为 |
| --- | --- |
| 已有文字以 `.?!` 结尾 | 尾部静音达到 **0.6 秒**就结束当前话语 |
| 已有文字尚无句末标点 | 等待更长的 **1.2 秒**静音，再结束当前话语 |
| 连续话语达到 **8 秒** | 回找已解码的最近句末标点，在该处结束前半段，并把后面的音频带入下一段 |
| 话语达到 **20 秒**仍未被前述规则结束 | 强制结束；不保证这个位置是完整语义句末 |
| 没有识别文字，静音达到 **2.4 秒** | 重置状态，不输出一个空定稿 |

源码确实实现了这些分支。8 秒是开始寻找合适句末的阈值，不是每 8 秒机械截断；它通过词的时间戳回切音频，并保留后续音频继续识别。这部分依赖本地 ASR 的 token 时间信息，不能直接套在百炼只返回片段文字的路径上。[配置](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/config.py#L117-L145)、[条件判定](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/asr.py#L451-L497)、[回切及尾部延续](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/asr.py#L499-L563)

它仍可能在句中长停顿或 20 秒上限处分开一段话；源码没有一个通用的“把两次已定稿半句重新合并成完整句”机制。翻译层承认端点产生的片段可能不是整句，因此把前文用空格连接作为翻译背景，默认最多三条。背景补充可以帮助翻译理解，却不等于修正显示段落。[翻译背景处理](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/translate.py#L148-L170)、[背景条数](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/config.py#L153-L168)

**Qwen3-ASR 路线不同。**核查提交的 `asr_qwen.py` 实现了标点感知静音和 20 秒上限，但没有 Nemotron 的 8 秒回溯标点切分。不能因为两条路线共用配置文件，就说它们都有相同分段能力。Qwen 路线结束时还会对整段音频做二次识别，再作为定稿和翻译输入。[Qwen 端点实现](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/asr_qwen.py#L336-L370)、[Qwen 二次识别](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/asr_qwen.py#L398-L416)

### 增量字幕与翻译怎样出现

原文 partial 直接刷新活动区域。实际代码还包含临时译文：当前原文比上次多出至少 **6 个以空格分开的词**，并包含 ASCII `.?!` 中任一符号时，提交一份翻译预览；更新的预览会使排队的旧预览失效。定稿后再以二次识别结果重新翻译，替换预览。该触发方式偏向英文，不能直接用于不靠空格分词的中文。[预览触发](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/cli.py#L313-L345)、[预览序号与定稿失效](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/translate.py#L107-L120)、[队列处理](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/translate.py#L239-L269)

这里的临时译文不是每个生成 token 都上屏。虽然内部调用 `stream_generate`，`_generate` 会收集所有 token，拼成字符串后才返回；其逐 token 迭代主要用于把 MLX 锁让回给 ASR。可以说它有“按增长片段刷新译文”，不能说它已经实现译文逐 token 输出到字幕。[生成循环](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/translate.py#L185-L221)

README 与翻译模块顶部仍写“只翻译定稿，不翻 partial”，但上述 `submit_preview` 已连通，因此该描述滞后于代码。[README 对照](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/README.md#L5-L14)、[模块说明对照](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/translate.py#L1-L10)

### 原译配对和历史显示

它用 **音源 label＋话语开始时间 started_at** 标识同一话语。原文定稿后不消失，继续留在活动区域，已有临时译文也保留；正式译文返回时填入同一 pending 条目，然后按原话语顺序把英文、中文一起提交到历史。由此避免所有英文堆在上面、所有中文堆在下面。[活动区域](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/render.py#L176-L200)、[预览与定稿维护](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/render.py#L248-L310)、[匹配与按序提交](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/render.py#L334-L373)

在已审查的渲染路径中没有按长段加“展开全文”按钮。超出终端的文字使用换行与历史滚动。但它有另一种妥协：等待正式译文的条目超过 **8 条**时，提前提交最老条目，使用已有预览或只显示原文；后来才到的正式译文可能被丢弃以避免乱序。这个限制不适合我们要求完整保留、可修订的课堂记录。[队列上限](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/render.py#L73-L76)、[迟到译文与提前提交](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/render.py#L355-L381)

### 日志何时可读

译文预览仅送终端，不写文件。开启翻译时，文件中的定稿原文也会先排队，等正式译文到达后按原译对写入并 `flush`；关闭翻译时原文直接写入。翻译禁用或退出时释放尚未配齐的缓存。这能得到整齐的最终文本，但 AI 想在课堂进行中读取“刚才尚未译完的原文”时可能暂时读不到，因此不能替代我们要求的实时 interim／revision 日志。[预览只显示不写盘](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/cli.py#L283-L297)、[文件写入](https://github.com/six-ddc/livecaption/blob/da182e0ae496743d975d4de556d3b6e450698a5c/livecaption/render.py#L414-L489)

## abb128/LiveCaptions

该项目是 Linux 桌面的英文实时转写工具，README 明确当前只支持英文；不是中英双语翻译器。它用 aprilasr 的 token 与 partial／final 事件驱动显示。[项目说明](https://github.com/abb128/LiveCaptions/blob/93734270e69a9d5d8a349075604477681c308dfa/README.md#L1-L20)

显示缓冲是两行。文字累积到窗口宽度时，向前寻找词边界换行；这属于排版，不是把话语判断为一个语义段落。partial 会重写尚未固定的部分，final 则固定已经显示的前缀，后续文字仍可接在当前行上。识别完成没有自动制造一条段落分隔线；独立的 silence 事件才请求换行。[两行定义](https://github.com/abb128/LiveCaptions/blob/93734270e69a9d5d8a349075604477681c308dfa/src/line-gen.h#L25-L30)、[按宽度与词边界换行](https://github.com/abb128/LiveCaptions/blob/93734270e69a9d5d8a349075604477681c308dfa/src/line-gen.c#L240-L257)、[固定前缀并继续当前行](https://github.com/abb128/LiveCaptions/blob/93734270e69a9d5d8a349075604477681c308dfa/src/line-gen.c#L280-L291)、[识别事件](https://github.com/abb128/LiveCaptions/blob/93734270e69a9d5d8a349075604477681c308dfa/src/asrproc.c#L123-L164)

旧文字滚出两行字幕，历史在独立窗口回看，也可导出文本。值得借鉴的是实时视图与历史记录分工，不能将它视为已经解决双语句对齐的方案，也不能把它的历史导出当作我们需要的实时可读事件日志。[历史窗口](https://github.com/abb128/LiveCaptions/blob/93734270e69a9d5d8a349075604477681c308dfa/src/livecaptions-history-window.c#L119-L145)、[文本导出](https://github.com/abb128/LiveCaptions/blob/93734270e69a9d5d8a349075604477681c308dfa/src/history.c#L187-L215)

## 对 LiveCaption 的可迁移结论

1. **采用“当前可修订字幕＋已稳定历史”的结构。**原文先显示，译文随后补到对应条目；已有文字无需等下一句话才上屏，也不因等待译文消失。
2. **句末、停顿和长度分别承担不同职责。**句末判断主要保证读得通，停顿提供附加证据，长度或时间仅用来限制等待。上限触发不能被包装成语义分段成功。
3. **保留跨片段连续性。**“这意味着，有时我们”与“会被赶出去。”如果来自两个云片段，显示层仍需允许连成一句；云端 final 只结束那个来源的更新，不必强制产生屏幕分隔线。
4. **借鉴原译文稳定配对，不复制按到达次序配对。**这些项目能够用任务快照或本地话语标识确定来源；我们应继续使用百炼实际提供的关联，再维护独立的显示范围。
5. **不搬用主窗口截前缀、20 秒强切、丢弃迟到译文或等待翻译才写日志的取舍。**我们的连续阅读和 AI 追课需求比它们对应的显示／日志策略更严格。
6. **要区分借鉴显示与更换翻译架构。**先转写、按可控文字单元翻译，可以从请求发出时就绑定原译关系。当前百炼直接语音翻译只能先使用云端给出的关联范围；把云端长范围再拆成更细的双语对，需要额外对齐证据。源码比较支持前一种架构更容易控制排版边界，但不能证明其翻译质量更高或实际延迟更低。

这些源码提供的主要参考，是明确什么时候保留半句、什么时候固定句界、怎样更新对应译文，以及怎样在保留内容的前提下控制显示。对当前项目，应优先验证这些状态和显示结构，再比较具体分句器。具体阈值和我们的效果仍应以本机文字事件回放验证，不能直接照抄其他项目的数字。
