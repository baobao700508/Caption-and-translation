# 字幕智能分段与真人录音验证

交付版本：LiveCaption 0.1.3（build 4）。桌面 `LiveCaption.app` 指向已构建的应用，双击即可打开；打开应用不会自动开始录音。

字幕重排已实现并经过真实文字模型、真人录音和原生渲染检查。本文记录 0.1.3 的分段功能验收：书面同译的完整输入通过，同传出现连接中断，Google 客户端的收尾判定错误导致严格检查失败。当前 0.1.4 的恢复策略、Google 修复及真人复测见[断线恢复与收尾验证](断线恢复与收尾验证.md)。

## 字幕具体怎样处理

原文、译文收到后立即显示并进入日志，不等待重排。每个明确关联的原译文段落定稿后，把两条文字一起交给可配置的小模型，让它选择语义对应的分组位置。长段持续增长、迟迟没有定稿时，在出现句末标点的前提下，按至少约 8 秒的间隔尝试整理前缀；没有整理的尾部继续完整显示。

屏幕使用“这一小组英文 → 对应中文 → 下一小组英文 → 对应中文”的顺序。中文、英文不必具有相同句子数，一句对两句可以留在同一组。下一次请求带上上一显示组的末尾，给跨云端段落的半句话重新接续的机会。回看历史时保持当前排版，点击“回到最新”恢复跟随。

此前按长度截掉正文、再要求点击展开的行为已移除。字幕完整换行并可滚动，不再出现“展开本段全文”，也不以省略号替换正文。

实现使用 Swift 的后台异步任务和 OpenAI 兼容 Chat Completions 接口，没有增加本地神经网络或 GPU 依赖。模型只返回普通 JSON 切点，不生成用于替换正文的文字，也不要求服务端支持 JSON Schema、`response_format` 或工具调用。本地程序从原输入切出显示片段，检查切点有序、覆盖完整，并验证拼接后的原文、译文分别逐字节一致。越界、遗漏、重复覆盖、无效格式均不采用。

失败最多重试一次。新段到来可以取消旧请求；即使旧请求晚到，也须通过会话、连接代次和原始字节匹配检查。积压时优先整理最新部分，没来得及整理的文字仍完整显示。模型服务断开不会阻塞收音、原始字幕或课堂日志。

语义分段仍有模型能力边界：真人样本中个别从句被单独分成一组，例如“his eyes fixed upon his friend”。逐字节校验能保证不改字，不能证明每个切点都是最佳切点，也不能修正原转写已有的错误。

## 模型如何选择

打开应用设置 → 字幕与外观 → 字幕智能分段，可以修改 API 地址、Key 和模型 ID，读取服务的模型列表并选择，最后点击“保存重排配置”。模型 ID 也可以手动填写。桌面 `LiveCaption配置.json` 已加入独立的 `captionReflow` 区域，其他配置字段保留。

本机已配置：

| 项目 | 值 |
| --- | --- |
| 文字服务 | 本机 CPA，`http://127.0.0.1:8317/v1` |
| 模型 | `gpt-6-luna` |
| reasoningEffort | `low`，服务不支持时可留空 |
| 每次超时 | 12 秒 |
| 最多重试 | 1 次 |
| 启用状态 | 开启 |

选择这里的模型只影响文字分段，不替换百炼翻译或 Google 转写模型。开启后，待整理的原文和译文会发送到所配置的文字服务。API Key 保留在本机配置和按地址隔离的 Keychain 项中，不进入本报告、课堂日志或 UserDefaults。

## 真人录音和验证方式

样本来自 [OpenSLR 的 LibriSpeech test-clean](https://www.openslr.org/12/)，是 LibriVox 的真人有声书朗读，许可为 CC BY 4.0。语料由 Vassil Panayotov 在 Daniel Povey 协助下整理。使用说话人／章节 `6930/75918` 的 `0000` 至 `0006` 七条连续语句，按章节顺序各输入一次，共 **76.145 秒、1,218,320 个采样点**。保留官方参考转录文本。

FLAC 无损解码为 16 kHz 单声道 PCM16；没有合成、循环、插入静音、调增益或添加降噪。PCM SHA256 为 `d08d93fcd77edd72c20341646f98131b6250c46ca9180e1d3053d689a9ebed9b`。来源、每条文件、时间区间和参考文本见 [样本清单](../TestResults/fixtures/librispeech/provenance.json)。

真人文件按真实时间经过实际 AppSession 输入队列、云连接、字幕投影、后台重排、原生字幕视图和日志。每次实际上传 WAV 与原始 PCM 比较；百炼同时检查送入编码器的观察轨。本次没有打开物理麦克风、系统采集或扬声器，不据此宣称降噪、远场课堂和物理译音播放通过验收。

## 结果

下表为长段触发逻辑完成后的真人录音结果。首字时间从文件开始输入计算，不是每个词说完到屏幕的延迟。

| 模式 | 实际输入完整性 | 首条原文／译文 | 运行中重排 | 结论 |
| --- | --- | --- | --- | --- |
| 书面同译 | 上传轨、编码器观察轨均逐字节一致 | 3.034／3.055 秒 | 7 次，单次约 1.142～6.271 秒 | 本轮通过；最终 16 组，原文和译文各自逐字节保留，运行中日志可读，收尾确认收到 |
| 原文转写 | 上传轨逐字节一致 | 1.632 秒／无译文 | 7 次，单次约 1.100～2.655 秒 | 字幕、分段、日志检查通过；正式末段已返回，但客户端未据此确认收尾，0.1.3 严格验收结果保留为失败 |
| 同声传译 | 上传轨少 56,000 个采样点，即 3.5 秒；编码器观察轨另少 2,400 点 | 2.983／3.012 秒 | 6 次，含两次请求重试后成功 | 约 51 秒发生连接失败并重连，本轮失败；返回的译音已保存，但没有播放到物理扬声器 |

书面同译的前台字幕先于第一轮重排出现：首条译文约 3.055 秒，第一次排版完成约 6.356 秒。重排期间，字幕与日志继续更新。原始文字与重排文字的逐字节比较，针对当前连接代次；跨连接的完整历史仍在原始日志里。

同一份音频的其他有限对照也保留：关闭重排的书面同译完整通过；一轮同传完整通过并收到译音；另一次书面同译在约 51 秒断连，上传少 3.4 秒。通过和失败均留档，没有用后续成功覆盖此前失败。现有证据不足以把连接中断归因于重排、供应商或网络，也不能宣称它已经修复。

其他检查：

- **32 项离线检查通过**：含 Unicode 保真、错误切点拒绝、先显示后请求、取消与迟到响应、原文修订、连接隔离、长段尾部保留、一次重试、积压边界，以及既有音频与协议检查。
- **26 项真实 CPA 文字检查通过**：包括双语保真、Transcribe 单轨重排、运行中日志、任意模型 ID 保存与其他配置字段保留、原生设置控件渲染。最后一组文字检查中三次重排耗时为 5.278、2.415、3.992 秒；其他保留的文字运行曾出现约 19 秒的整理等待，所以不承诺整理请求固定在几秒内完成。
- **14 项原生字幕布局检查通过**：覆盖四分钟文字事件、原译文相邻、仅原文／仅译文、同传共用视图、手动回看、返回最新、小窗口和正文不折叠。该项为本地文字事件渲染，不是四分钟真人语音测量。
- Release 构建和应用签名验证通过，版本为 0.1.3（4）。原生视图由 NSHostingView 渲染并核对截图／文字；没有把离屏验证说成真实鼠标操作验收。

真人单样本的参考文本比较也保存于 `metrics.json`。它只能说明这个朗读样本的转写差异，不能作为模型排名或翻译准确率评测。

## 0.1.3 的连续性与收尾问题

百炼两次失败都记录为原生 WebRTC 的 ICE failed 状态。失败前，本机输入消费持续进行，记录中的输入 underflow 为零；这不支持“本机周期性补零导致这次断连”的解释，但客户端发送计数也不能证明服务器实际收到。根因尚未隔离，同传连续稳定性仍未通过。

Google 在 0.1.3 停止时已返回正式末段，客户端却在固定等待两秒后返回失败。该版本日志因此保留 `tail_incomplete`，不能把这个标记解释为 Google 没有返回最终文字。供应商最终文字仍不是逐采样点的消费回执。

这里交付的是字幕重排机制、可配置模型以及可复现的真人测试，未更改音频前处理、百炼连接协议或 Google 收尾协议。干净单人朗读的结果不能代表嘈杂课堂、多人同时说话或远场麦克风效果。

在项目目录运行以下命令，三种模式使用同一个有限真人样本。它们不播放音频、不采集环境声音，但会调用所选配置中的真实云 API：

```bash
bash scripts/check.sh
bash scripts/verify-caption-layout.sh
bash scripts/verify-human-app.sh subtitles
bash scripts/verify-human-app.sh speech
bash scripts/verify-human-app.sh transcribe
```

`scripts/prepare-human-fixture.py` 保留公开样本来源并校验 PCM 哈希；`scripts/analyze-human-reflow.py <result.json>` 重新计算输入完整性、当前代次文字保真、首字时间和重排耗时。实际录音位于各结果的 `log_path/audio/uploaded.wav`，收到的译音位于同目录 `translated.wav`。
