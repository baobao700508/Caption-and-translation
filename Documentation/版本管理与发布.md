# 版本管理与发布

LiveCaption 从 GitHub Release 下载，解压后复制到“应用程序”运行。SaT、WhisperKit、Google 和百炼属于同一个应用的可选功能，不分别发布应用。已安装的 App 不依赖源码目录；构建脚本不创建桌面符号链接，也不替换“应用程序”里的版本。

## 源码与版本

主工程 `Sources/`、`Tests/`、`Resources/` 和 `scripts/` 是合并后的源码。`Experiments/` 内的工作副本用于验证，不能直接交付。

版本只在 `Resources/Info.plist` 定义。`CFBundleShortVersionString` 表示应用版本，`CFBundleVersion` 使用递增整数，Sparkle 用构建号判断是否有新版。正式发布不得使用 `15.1` 一类独立追加的构建号，也不能把较旧工作副本的版本覆盖到正式包。

实际本机构建记录保存在 `Releases/current.json`，包括版本、构建号、可执行文件 SHA-256、源文件清单、检查结果和旧包归档位置。已安装应用的版本以其“关于”和设置窗口显示为准；本机构建成功不代表 GitHub Release 已发布或用户已安装。

## 更新机制

设置窗口左下角、应用菜单和菜单栏右键菜单提供“检查更新…”。结束记录后可检查，网络访问和安装提示由 Sparkle 2 承接，不在采集中自动重启。应用从固定 HTTPS 地址读取更新源：

```text
https://github.com/baobao700508/Caption-and-translation/releases/latest/download/appcast.xml
```

每个 Release 的 `appcast.xml` 指向该版本固定标签下的 ZIP，不指向临时链接。更新列表与归档均有 Ed25519 签名；应用在解析更新列表、解压更新包前验证签名。公钥随 App 分发，私钥只保存在发布者本机，不进入 Git、应用包或 GitHub Release。

配置、macOS 应用偏好、本地模型与会话日志位于应用包之外，更新只替换 App。安装后保留原有 bundle identifier，服务凭据仍沿用原有存储方式。0.1.27 以前的版本没有更新器，需先手动安装支持更新的版本。

当前发布使用本地 ad-hoc 签名，没有 Developer ID 和 Apple 公证。Ed25519 保证更新包来源与完整性，不能替代首次安装的 Gatekeeper 信任；本机验收也不能代替全新 Mac 的安装验收。

## 准备签名密钥

首次发布时运行：

```bash
swift scripts/create-update-key.swift
```

命令只打印公钥。已有私钥时复用，不覆盖；新私钥保存在 `~/Library/Application Support/LiveCaptionRelease/ed25519.key`，目录权限 700、文件权限 600，不查询钥匙串。将公钥填入 `Resources/Info.plist` 的 `SUPublicEDKey`。妥善离线备份私钥；丢失私钥后，当前本地签名应用无法继续通过同一更新链验证新版。

## 构建和打包

退出现有 LiveCaption，在主工程执行：

```bash
bash scripts/build.sh --archive-legacy
python3 scripts/package-release.py --notes /absolute/path/release-notes.md
```

构建入口调用 `scripts/release.py`，同一时间只允许一个发布任务。先运行主工程检查，在独立暂存目录构建并验证签名，再用同一可执行文件执行原生界面检查。构建期间源文件发生变化、检查失败、构建号未递增或仍有旧实例运行时，不发布新包。SwiftPM 公开依赖下载禁用钥匙串和 netrc 凭据查询。

验证通过后，旧构建包移入 `Releases/Archive/`，新包放到 `dist/LiveCaption.app`。`--archive-legacy` 同时归档 `dist/` 内的其他旧包；`--activate` 仅用于打开本地构建包验证，日常使用应从 GitHub 安装。归档不删除历史录音、日志和测试证据。

打包命令校验 App 与通过检查的源码、可执行文件一致，生成 `Releases/GitHub/v版本-build构建号/`，包含 ZIP、SHA-256、已签名的 `appcast.xml` 和发布说明。使用 Sparkle 官方工具生成和验证签名，并显式读取本机私钥文件。`--key-file` 可指定另一个受保护的文件；不使用钥匙串回退。

## GitHub Release

为已提交的对应源码创建 `v版本-build构建号` 标签。创建 GitHub Release，填入用户可读的中文发布说明，上传打包输出中 `github-release.json` 列出的三个文件：ZIP、ZIP 的 `.sha256` 和 `appcast.xml`。资产上传完整后再发布并设为最新版本，避免用户读到不完整的更新源。不要上传本机私钥、配置、录音、日志或验证资料。

发布后从公开 Release 地址读取 `appcast.xml`，确认下载地址、构建号、签名与归档长度一致，再从较老的已安装版本通过原生界面完成升级。检查版本提升、安装路径、重启后的窗口和更新结果，并核实配置、模型、日志保留；源码构建检查不能替代此流程。

检查、界面结果和源文件清单保存在 `TestResults/release-版本-构建号-时间/`。这些检查验证应用和发布路径，不代表重新测量了云端延迟或整节课稳定性。

## 独立开发

开发改动先合并到主工程，再统一发布。需要隔离验证包时，为 `scripts/build.sh` 显式设置 `LIVECAPTION_APP_PATH`，输出到自己的实验目录；不得指向 `dist/LiveCaption.app` 或已安装 App。独立验证包只在测试期间运行，不另设正式版本号或抢占用户日常入口。
