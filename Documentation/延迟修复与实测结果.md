# LiveCaption 延迟修复与实测结果

2026-10-21，Apple Silicon、macOS 26.6，北京百炼 `qwen3.8-livetranslate-flash-realtime`。

## 结论

客户端的长时间发送积压、由积压造成的丢音，以及停止时译音被截断，已有可复现的定位和修复。Translate 的纯字幕、字幕加声音均采用原生 WebRTC／Opus；Transcribe 保留独立 Google 线路。现有凭据继续使用，桌面配置不需要增加新的 Key。

五句已知内容的实际应用测试中，中文整句在语音句末后约 0.34–1.38 秒进入字幕日志；同传收尾检查确认最后一句译音保留。另一段 60 秒真实录音的客户端丢包和编码器输入 underflow 为零。这些是限定音源和环境下的结果，不能推定为整堂课准确率、所有网络或所有音量的保证。

## 具体改了什么

核心改动是更换两种 Translate 模式的音频传输实现，继续使用同一个百炼模型。书面同译与同声传译共用修复后的连接，区别仅在于是否请求并播放译音。原文转写继续使用独立 Google 线路。这次没有调整麦克风降噪、增益或采集设备。

### 1. 将翻译音频从 WebSocket 原始音频发送改为原生 WebRTC／Opus

**原问题：**原始用户会话采集约 198.5 秒，客户端成功发送轨仅有 79.6 秒，单次发送最长阻塞 12.738 秒，已有 123 条缺口事件。麦克风原片与对齐输入时长一致，没有此前每 100 ms 周期性填零的现象；长积压有独立发送证据。

对同一真实录音进行 TCP 观测时，发送缓冲持续达到 131,072 字节，对端接收窗口仍有空间，记录到 211,011 字节重传。改变 WebSocket 实现、分包和接入地址，没有得到可接受的连续性。证据将问题缩小到这条连接的传输表现，不能定位为某一家运营商或某一个远端节点的责任。

**代码改动：**增加 Swift `BailianWebRTCTransport` 和 Objective-C++ `WebRTCBridge`，将百炼正式连接工厂及直接构造器的默认实现都切到原生 WebRTC。音频以 Opus 编码后走 RTP 媒体轨，最大编码码率设为 32 kbps；会话配置、字幕和控制事件走 DataChannel。共用接口内部仍会接收原有音频 append 对象，但其 Base64 在本机解码后交给编码器，不再作为网络音频负载发送。

**新增技术：**固定版本 WebRTC M155 原生框架、Opus 编码、自定义 `RTCAudioDevice`，通过 HTTPS 交换 SDP 建立连接。框架由构建脚本下载并校验 SHA-256，随应用打包。正式应用没有采用 AOQ 或隐藏网页的 WebRTC 实现。

**音频处理边界：**自定义设备只消费原采集链路提供的 PCM，不打开第二个麦克风或扬声器。网络 SDK 的额外回声消除、降噪、高通与自动增益均关闭，避免重复处理。Apple 麦克风处理和系统声音处理继续由原采集链路承担。

**验证：**60 秒真实录音连续发送一次，960,000 个有效样本全部进入编码器；客户端队列丢包、原生输入 underflow、结束时待消费样本均为零。最长客户端写入约 4.50 ms，最长排队约 2.15 ms。该结果证明这次测试的客户端积压与输入缺口得到控制，不等于服务端逐包确认，也不等于所有网络都能保证同样表现。

### 2. 修正会话配置与音频发送的先后顺序

**原问题：**原生库即使 track 静音或置空，仍可能发送静音 RTP。服务端会提前进入 started 状态，随后拒绝模型会话配置。

**代码改动：**配置确认前将 RTP encoding 设为 inactive，收到 `session.updated` 才启用。增加重复 `session.created` 防护，只发送一次初始化配置；核验服务端回显中的模型、目标语种、输出模态、格式与检测方式。课堂停顿检测使用 `server_vad`，未设置文档未声明支持的 3.8 灵敏度参数。

**验证：**真实回放统计中，配置确认前 RTP 包为零；服务端会话配置校验通过。重复 greeting 的防重逻辑另有离线检查。

### 3. 修正新传输的供音缓冲和最后不足一帧的样本处理

**原问题：**前端按约 100 ms 提供音频，WebRTC 每 10 ms 消费一帧。最初 100 ms 起始缓冲不足以吸收一次约 118 ms 的调度停顿，60 秒回放曾出现 1,920 个 underflow 样本。另一个边界错误是最后不足 160 个样本时无法排空输入。

**代码改动：**自定义设备用独立线程按 10 ms 供音，起始缓冲改为 200 ms，队列上限为一秒；合并后的大包切成不超过 3,200 字节的小块。缓冲满时重试同一块，成功前不跳过它。停止时消费所有剩余有效样本，只为编码帧补齐必要的零，并单独记录补齐量。

**验证：**原先失败的 60 秒回放重新运行后 underflow 为零。另一份 17.3139375 秒、277,023 个样本的语音包含不满一帧的尾部；输入录音与编码器有效输入样本数、字节均完全一致，尾部没有丢失。200 ms 是起始缓冲成本，没有设置十几秒的攒句缓冲。

### 4. 修正结束记录时译音被提前截断

**原问题：**DataChannel 的 `session.finished` 可以早于 RTP 译音尾部到达。原实现收到它便关闭连接，保存的声音停在“需求量”，缺少“减少”和最后一句。

**代码改动：**在原生桥接层延后交付终止事件，同时继续接收并保存解码音频。至少等待 500 ms，并确认连续 350 ms 没有新的非零输出后再结束；最长等待八秒，超时报告尾部不完整。停止阶段仍保存译音，避免界面进入停止状态后遗漏尾部数据。

**验证：**同一组五句话的译音由截断时的 10.60 秒增加至 13.77 秒，收尾等待约 1.90 秒，录音末尾约 197 ms 静音。独立 Google 转写确认“需求量减少”及最后一句“四点三十分结束”均存在。收尾等待发生在停止阶段，不是持续字幕延迟。此项没有用人工试听代替或补充判断。

### 5. 修正“目标中文，浮窗只显示英文”的显示问题

**原问题：**翻译会话中可以已经收到中文，但遗留的“仅原文”显示偏好将译文隐藏。原始问题会话有 87 条中文翻译事件，不能仅凭屏幕上的英文断言服务端完全没返回中文。

**代码改动：**字幕顶部增加“原文／译文／双语”选择；对旧版遗留的仅原文偏好执行一次双语迁移，随后仍允许用户自行选择。翻译内容与原文分别维护和显示。

**验证：**两种翻译模式通过实际应用状态和原生字幕视图回放，保留双语截图，中文字段有内容。此项解决显示隐藏，不代表翻译准确率或传输延迟同时得到证明；后二者分别测试。

### 6. 增加能检查真实数据经过哪里的录音和测量入口

**代码改动：**保留 `uploaded.wav`，增加 `webrtc-input-observed.wav` 和 `translated.wav`，分别对应客户端接受的 PCM、实际送入编码器的有效 PCM、收到的解码译音。增加原生消费量、待消费量、underflow、补齐量与首段译音接收时间的诊断记录。

增加有限文件回放入口，使用正式 AppSession、正式发送队列、默认连接和字幕视图；测试中不打开硬件麦克风，不播放扬声器。延迟分析重建字幕追加和修订后的完整句子，再与音源句末比较，避免把某个零碎 delta 当作整句完成。

**验证：**比较音源、客户端接受轨、编码器输入轨的有效 PCM 字节；在会话仍 active 时读取 `live.md`，确认 AI 无须等停止记录就能读取文字。两种翻译模式分别检查无译音／有译音，原文转写另做回归。增加测量手段本身不算延迟修复，具体结果见后续表格。

## 改动位置与覆盖范围

| 代码位置 | 具体责任 | 影响模式 |
| --- | --- | --- |
| `Sources/LiveCaptionCore/ProviderConnection.swift`、`BailianConnection.swift` | 默认连接切换；共用初始化、配置核验和消息解析 | 书面同译、同声传译 |
| `Sources/LiveCaptionCore/BailianWebRTCTransport.swift` | SDP 建连、PCM 分块与背压重试、输入排空、控制消息收发 | 书面同译、同声传译 |
| `Sources/WebRTCBridge/WebRTCBridge.mm` | 原生 WebRTC、Opus、RTP 启停、10 ms 供音、缓冲和译音尾部排空 | 书面同译、同声传译 |
| `Sources/LiveCaptionCore/AudioArchive.swift` | 编码器输入对照轨与返回译音存档 | 录音诊断；两种翻译模式 |
| `Sources/LiveCaptionApp/AppSession.swift`、`Views.swift` | 原文／译文显示、旧偏好迁移、停止阶段保存译音、共用发送入口 | 字幕显示与会话管理 |
| `Sources/LiveCaptionApp/FileReplaySmoke.swift`、`scripts/analyze-caption-latency.py` | 正式应用有限回放、运行中日志与逐句延迟验证 | 两种翻译模式；另有独立转写回归 |
| `scripts/setup-webrtc.sh`、`scripts/build.sh` | 固定 SDK 下载校验、框架打包与签名 | 应用构建 |

此前已单独修过采集时间轴 100 ms／40 ms 不匹配造成的周期性填零。它与这里的网络积压、原生供音调度和译音收尾是不同缺陷，不能用其中一项通过来代替其余项目验收。外部低音量识别、整堂课准确率和实体扬声器体验仍需各自的证据。

## 实际应用字幕与运行中日志

有限语音序列包含五句不同的英文，不循环播放。它用于提供已知内容和句末时间；另有真实课堂录音检验连续性。

| 已知语音内容 | 书面同译句末至完整中文 | 同传句末至完整中文 |
| --- | ---: | ---: |
| 截止日期是周一，不是周五 | 0.343 s | 0.383 s |
| 课程解释供给与需求 | 1.257 s | 1.258 s |
| 课程继续时保存 transcript | 0.831 s | 0.790 s |
| 价格上涨导致需求量减少 | 1.377 s | 1.359 s |
| 讲座四点三十分结束 | 1.089 s | 1.142 s |

句末采用 10 ms 粒度的音量检测估计；接收端使用实际日志中可重放的字幕修订，计算首次形成完整句子的时间。它不是逐词强制对齐，也没有用摄像机测量屏幕刷新或物理扬声器延迟。冷启动的连接准备时间另外发生在文件输入之前，不并入上述字幕时效。

同传首段解码译音在第一句语音结束后约 0.627 秒收到。该时间点来自实际应用的 `translation.audio.first_received`，不是声音从实体扬声器发出的时间。

测试直接运行打包应用的 AppSession、正式发送队列、默认连接、字幕状态与原生字幕视图。运行到一半时读取 `active` 会话的 `live.md`，确认文字已可供外部 AI 使用；结束后确认尾部完整和录音字节一致。测试不采集现场音，也不播放扬声器。两种模式的实际字幕截图分别位于 `TestResults/app-replay-subtitles/caption.png` 与 `TestResults/app-replay-speech-drained/caption.png`。

书面同译返回译音样本数为零。同传返回的译音单独保存在该会话 `audio/translated.wav`，由独立 Google Transcribe 再次识别，得到五句话，包括否定关系“周一，不是周五”和最后一句“四点三十分结束”。这证明测试录音中有可辨认的完整内容，不是人工音质或物理播放验收。

模型仍有译词错误：同一测试中的 `transcript` 被译成“讲义”或“笔记”。原文记录保留了正确英文。真实录音中的人名等也有识别差异；未进行整段人工逐词校对，不能报告 WER 或声称零漏字。

## 真实录音连续性

使用原正常会话录音的第 30–90 秒，连续发送一次，不循环。它与首个 30 秒对照使用不同内容。

| 项目 | 结果 |
| --- | ---: |
| 音源时长 | 60.0 s |
| 有效输入样本 | 960,000 |
| 客户端队列丢包 | 0 |
| 原生输入 underflow | 0 |
| 结束时原生待消费样本 | 0 |
| 配置确认前 RTP 包 | 0 |
| 最长客户端写入 | 约 4.50 ms |
| 最长客户端排队 | 约 2.15 ms |
| 正常结束确认 | 收到 |

音源、客户端输入录音、原生编码器输入对照逐字节一致。客户端输入和编码器输入不是服务端解码回传，不能把本地接受输入当作远端逐包确认。

使用显式测试配置复现有限文件回放（需要实验传输 SDK）：

```bash
swift run LiveCaptionVerify /absolute/path/recording-16k-mono.wav translate /absolute/path/test-config.json subtitles
swift run LiveCaptionVerify /absolute/path/recording-16k-mono.wav translate /absolute/path/test-config.json speech
swift run LiveCaptionVerify /absolute/path/recording-16k-mono.wav transcribe /absolute/path/test-config.json
```

正式应用为 `dist/LiveCaption.app`，版本 0.1.1。构建和 ad-hoc 签名校验通过；22 项离线检查通过。应用不链接 AOQ 或 WebKit 实验实现。没有重新采集麦克风，没有上传承诺仅在本地保留的六秒低音量样本，也没有播放实体扬声器或要求用户配合。
