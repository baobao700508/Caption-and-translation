# 实时字幕分段方案调研

## 结论

LiveCaption 需要一个独立的增量文本分段层。云端音频片段、原译文关联、文本句子、屏幕排版应分别处理。音频停顿可以辅助判断，但不能直接决定段落；长文也不应靠省略正文和“展开全文”维持可读性。

截图中的“这意味着，有时我们 / 会被赶出去。”应作为连续的一句话处理。即使两部分来自不同云端消息，后半句仍应接回未完成的句子。文字应立即可见，只有“把前文固定成一个段落”这一动作需要等待足够依据。

推荐将 **Apple `NLTokenizer(.sentence)`＋跨云片段的可修订尾句**作为有标点线路的轻量对照基线，并将 **SaT/wtpsplit 的句界与段落边界预测**作为模型方案重点评估。SaT 的用途不局限于缺标点文本，官方明确提供段落分割接口。两条方案都需要独立的阅读排版、增量稳定策略与双语对应处理。原型必须先用既有文字日志回放验证，不能把更换分句器直接当成产品问题解决。FunASR 的在线标点模型确实接收增量文字，但它解决的是补标点，不能直接替代双语字幕排版与原译文对齐。

本机已验证 Apple 分句器对截图对应文字和中英文边界例子的实际行为。SaT、spaCy、PySBD、FunASR 尚未在本机课堂样本上做性能与准确率比较；其能力依据是官方文档、模型卡、论文与实现源码。

## 当前问题的直接证据

`CaptionParagraph.swift` 按明确的供应商原译文关联生成显示组，没有独立的文本句界判断。`CaptionTranscriptView.swift` 则根据窗口高度计算每条轨道的 1–3 行预览，截取末尾字符、加省略号，再提供“展开本段全文”。这分别造成了不合语义的块边界和必须点击才能看到完整正文的问题。

会话 `f0bce5b9-0a65-43ed-a84a-0849c80d0662` 的文字事件还原后，相邻两个译文片段分别结束于“这意味着，有时候我们 ”和包含“会被赶出去。”。这与截图暴露的断裂吻合，足以确认当前 UI 把供应商片段边界直接变成阅读边界不合适。

百炼文档把同一个 VAD 分段的原文 `item.id` 与译文 `previous_item_id` 关联起来；这是一种原译片段关系，不是句子完整性保证，也没有提供逐词或逐句的一一对应。音频停顿与 `done` 可辅助管理生命周期，不能单独决定是否另起阅读段落。[百炼服务端事件](https://help.aliyun.com/zh/model-studio/live-translator-server-events)

## 四种不同的边界

| 边界 | 回答的问题 | 是否直接作为屏幕段落 |
| --- | --- | --- |
| 音频片段边界 | 什么时候停顿或结束一个云端处理片段 | 否；一句话中途也可能停顿 |
| 文本句界 | 这句话是否说完，后面是否开始另一句话 | 可作为主要依据，但需允许尾部修订 |
| 语义段落边界 | 是否换了论点、例子或话题 | 需要更多上下文，不应让实时字幕等待整个话题结束 |
| 字幕显示块与换行 | 当前字号和窗口宽度下怎样方便阅读 | 是排版决策，不应改变原文、删字或伪造语义边界 |

专业字幕也会保护词组和句法连续性。例如 Netflix 的指南要求避免把主语代词与动词、助动词或否定词与动词拆开。该指南针对制作完成的影视字幕，其固定行数和时长不能直接套用在课堂滚动记录；可以借用的是按语言结构断行的原则。[Netflix 字幕通用要求](https://partnerhelp.netflixstudios.com/hc/en-us/articles/215758617-Timed-Text-Style-Guide-General-Requirements)

## 可用技术

| 候选 | 能做什么 | 文字流式输入的真实情况 | 中英文与部署边界 | 对当前项目的判断 |
| --- | --- | --- | --- | --- |
| Apple NaturalLanguage `NLTokenizer(.sentence)` | 对给定文本找句子范围；本机例子正确处理 `Dr.` 和 `3.14` | 每次处理当前字符串；应用负责连续缓存、修订和边界提交；返回最后一个范围不代表句子完整 | macOS 原生 Swift API，本机已测中文与英文；无额外模型下载 | 当前有标点线路首选原型基线；不能恢复缺失标点或纠正错误句号 |
| Unicode／ICU Sentence BreakIterator | 标准句界规则与可配置的缩写过滤 | 对文本窗口执行边界分析，需要应用自行管理增量状态 | ICU 有多语言边界规则；语言专用缩写过滤覆盖需分别核对 | 可控、可移植的规则基线；苹果原生方案足够时，无须为此另加一套运行时 |
| 规则句界检测、spaCy Sentencizer、PySBD | 利用标点、缩写等规则找句末，保留原文字面内容 | 普通文本调用；应用自行缓存未完成的尾部。spaCy 的 `pipe` 是文档流，不等于同一句文字不断追加的流式会话 | PySBD 明确有 `en`、`zh`，MIT；spaCy 可配置句末标点 | 适合作为有标点文本的基线。不能修复所有错误标点，也不能仅靠规则理解话题 |
| spaCy SentenceRecognizer／依存分析 | 训练式句界判断，可超出简单标点规则 | 对输入 `Doc` 处理；增量稳定策略仍需应用负责 | 需选择语言模型；官方提示口语、社交文本可能需要适配 | 可作离线比较项；为了字幕分句引入整个 Python NLP 管线，收益需实测 |
| SaT／wtpsplit | 预测句子边界，也支持 `do_paragraph_segmentation=True` 预测段落边界；不局限于补标点 | 公开 `split`／`predict_proba` 是文本批次接口；可在滑动文本窗口上重复推理，但没有据此证明可直接以 token 追加并永久缓存结果 | 官方支持中英文，代码与模型 MIT，提供 ONNX 路线；Swift 原生接入、课堂段落质量与端侧耗时需另测 | 重点评估的神经句界与段落候选；不生成译文，不自动提供双语对齐 |
| FunASR CT-Transformer `ct-punc` | 为无标点文字恢复标点 | 常用 `ct-punc` 是离线文本标点路线，不能因为“CT”或论文标题带实时就当成流式 API | 常用模型明确中英；模型卡 Apache-2.0 | 当前译文本来已有标点时，不宜无条件再补一次 |
| FunASR `CTTransformerStreaming` | 利用跨块缓存做在线标点恢复，考虑 VAD 位置 | 源码明确接受 `cache`，拼接历史未完成文字；专用在线模型与离线 `ct-punc` 不同 | 已核实实时 checkpoint `iic/punc_ct-transformer_zh-cn-common-vad_realtime-vocab272727`；官方页面标为中文，不能凭离线中英模型推断在线英语能力相同 | 适用于未来无标点转写线路的专项比较；需核对权重语言、导出运行时和尾部语义 |
| 大模型语义分段 | 根据论点或话题组织段落 | 普通流式输出不意味着接受一个持续追加、可回改的输入会话；仍需设计窗口、上下文和提交策略 | 会引入推理成本与额外等待，生成式输出还有改写风险 | 可用于课后整理，不作为实时字幕首选依赖 |

## Apple 原生方案的本机实验

在 macOS 26.6 上用 `NLTokenizer` 执行 12 个文本探针，显式指定中文或英文。输入包括既有日志还原的文字、截图手工转录的短例子，以及用于探查能力边界的构造例子。没有采集音频、上传内容、调用云端模型或改动应用。

| 输入／操作 | 实际结果 | 意义 |
| --- | --- | --- |
| 单独输入“这意味着，有时我们” | 返回一个包含整段输入的范围 | 不能把最后一个 token 范围当作“已完成句子” |
| 加上“会被赶出去。我们确实被赶走过。” | 分成两个完整句子 | 缓存尾句并跨片段续接，可解决截图这类断裂 |
| 原样连接日志中的两个相邻片段 | 最后一句成为“这意味着，有时候我们 会被赶出去。” | 无须改写文字即可跨供应商片段恢复连续句；保留原始空格 |
| 连续中文或英文没有标点 | 各自仍是一个范围 | 这个分句器不会自动恢复无标点语流的句界 |
| `Dr. Smith paid $3.14. He left at 4:30 p.m. The lecture continued.` | 正确得到三个句子 | 比直接按每个句点切割更适合英文 |
| “这意味着，有时我们。会被赶出去。”；对应英文错误句号例子 | 都沿错误句号切成两句 | 原生分句器不能保证修复上游错误标点 |
| 用 `.paragraph` 处理没有换行、但语义换了话题的文字 | 整体仍是一段；加入换行后才变为两段 | 不能把 `.paragraph` 当作自动理解话题的语义分段模型 |

实验脚本：[NativeSentenceProbe.swift](../Experiments/SubtitleSegmentation/NativeSentenceProbe.swift)。完整结果：[apple-nltokenizer-results.json](../TestResults/subtitle-segmentation-research/apple-nltokenizer-results.json)。这验证的是文本边界行为，没有测量生产字幕上屏延迟，也没有证明所有语言现象都能处理正确。

## 分段模型的实际能力

SaT 的官方 README 明确提供 Paragraph Segmentation：`sat.split(text, do_paragraph_segmentation=True)` 返回段落列表，每个段落内再包含句子列表，可通过 `paragraph_threshold` 调整段落边界阈值。实现使用模型预测的换行概率选择段落边界，因此不是只在输入已经存在的换行处拆分，也不必先恢复全部标点才能判断边界。[官方段落接口](https://github.com/segment-any-text/wtpsplit#paragraph-segmentation)、[概率与分割实现](https://github.com/segment-any-text/wtpsplit/blob/main/wtpsplit/__init__.py)

这是一种可评估的模型分段能力，但不能把它自动等同于课堂话题理解：模型预测哪里适合换段，字幕还需要检验段落是否过长、半句是否被切断、后文到达后边界是否稳定。官方的长度约束也不能直接替代这些验证，特别是硬性最大长度可能与语义完整性冲突。

另有专门针对话题变化的模型，例如 SECTOR：对文档划分连贯的主题区间并分类。其论文的 WikiSection 数据包含英文与德文的疾病、城市领域，不能据此推断它已适配中文课堂或实时字幕。话题分段适合进一步比较课堂笔记结构，而实时浮窗还需要比整段话题更细的阅读单位。[SECTOR 论文](https://arxiv.org/abs/1902.04793)

## 两个容易误选的地方

**SaT 的“支持短文本”不能写成“原生流式”。**论文中的基础 SaT 使用有限未来上下文，以减少对遥远后文的依赖；但论文也明确指出，监督混合版本 SaT+SM 关闭了这一机制。因此 `sat-3l` 与 `sat-3l-sm` 不能用同一种流式能力描述。当前库有 ONNX 推理接口，仍需在应用里管理窗口、尚未确认的尾部、跨更新一致性及上游修订。官方 GPU 批量吞吐不代表这台 Mac 处理每次字幕更新的延迟。[SaT 论文 §3、附录 A.1](https://arxiv.org/html/2406.16678v2)、[sat-3l-sm 模型卡](https://huggingface.co/segment-any-text/sat-3l-sm)、[wtpsplit 接口源码](https://github.com/segment-any-text/wtpsplit/blob/main/wtpsplit/__init__.py)

**在线标点也没有把每个 VAD 片段等同于句子。**FunASR 的在线实现保存上次未完成文字，寻找句号或问号作为可释放的上下文边界，并去除当前输出末尾的预测标点。这表明模型本身也给后续文字保留了影响句界的空间。源码中的超长缓存保护还可能把逗号提升成句末；这种工程保护不应被当成语义正确的证明。公开在线 checkpoint 的页面语言标注为中文，英语实测未完成。[CTTransformerStreaming 源码](https://github.com/modelscope/FunASR/blob/main/funasr/models/ct_transformer_streaming/model.py)

## 实时更新应怎样组织

以下是针对 LiveCaption 的应用层设计建议，不是任何候选库已经完整提供的功能。

1. **保留连续正文和来源。**云端 ID 用于追踪文本来源、修订和原译关系；界面段落拥有单独 ID。一段可以覆盖多个云片段，一个长云片段也可以包含多个显示块。
2. **最新文字立即显示，末尾保持可修订。**识别完成或 VAD 停顿不自动插入段落分隔线。跨片段的半句话先继续衔接；新文字到达时只重算尾部。
3. **句界由语言证据确认。**候选位置优先考虑句末标点及缩写、数字、引号等例外；缺标点时才比较模型边界预测。需要后文时等待的是边界确认，不是文字上屏。
4. **已稳定文字逐步固定。**把文本的稳定性与语义完整性分别判断；重复两次的前缀可能稳定，却仍只是一句的前半部分。云端明确修订已确认内容时，按来源映射修订原位置，不能把同一句再次追加。
5. **窗口不足时自然换行或滚动，正文不折叠。**长句可在合适的短语处做显示换行；这不必产生新的语义段落或日志断句。阅读历史时暂停自动跟随。

应用层可将相邻的一个或几个完整短句组织成阅读块。长度只作为软目标：优先在完整句子后结束；句子过长时允许自然换行，不按固定字符数或固定秒数硬切。真正的话题段落需要更多上下文，适合日志整理，不应成为实时上屏的前置条件。显示分组仅保存原文字范围与来源关系，供应商原始文字和修订事件继续完整写入日志。

稳定前缀有现成研究实践可借鉴：Whisper-Streaming 用 LocalAgreement，在连续识别假设间确认一致部分；后继 SimulStreaming 还采用需要模型内部注意力的 AlignAtt。对于只收到百炼云端文本事件的应用，不能假装拿到了内部注意力，也不能把每个新增 delta 当作一轮独立全文假设。可迁移的是“稳定前文＋可修订尾部”的状态管理思想，具体提交条件必须根据供应商事件语义制定。[Whisper-Streaming](https://github.com/ufal/whisper_streaming)、[SimulStreaming](https://github.com/ufal/SimulStreaming)

## 双语对应是独立约束

英文一个句子可能翻成中文两句，反之亦然。分别按句号切分后，按第一个配第一个、第二个配第二个，会制造错误对应。句界检测库不会自动提供双语句子对齐。

原译文应先保留明确的来源关联，再评估是否有可靠的更细粒度对应。没有细粒度证据时，可以将原文和译文放在同一个关联范围内，各自完整地分句阅读；不能声称每一行一一对应。跨云片段合并显示时，也必须保留这些范围，防止把一个片段的英文配到下一段中文。若将来引入跨语句对齐模型，应单独测漏译、合句、拆句与修订场景，不能把它藏在“分段”这个名称里。

长关联范围仍可能让“上面英文、下面中文”相距过远，因此解除折叠本身也不够。原型应同时比较两个可检验方向：有可靠细粒度对齐时显示短的原译配对块；只有粗粒度关联时，用两个固定可见的语言区域保证最新原文和译文都能看到，历史记录按关联范围回看。后者是显示方案，不应宣称实现了逐句对齐。两分钟连续讲话是必须覆盖的双语阅读测试。

## 验收应覆盖什么

| 场景 | 应有表现 |
| --- | --- |
| “这意味着，有时我们”之后停顿，再出现“会被赶出去。” | 连续完整一句；中间不停留一条永久段落分隔线 |
| “因为／但是／如果／which／because”后发生云片段结束 | 允许跨片段衔接，不因片段完成固定半句话 |
| `Dr. Smith`、`U.S.`、`3.14`、引号内问句 | 不把缩写或小数里的点机械当成句末 |
| 同一云片段连续讲话两分钟 | 已完成的句子可以持续组织成可读短块，最新文字可见 |
| 英文一长句、中文两短句；中途补改译文 | 全文无遗漏、无重复，不强行按句序伪造配对 |
| 长时间无标点 | 文字持续上屏；模型／规则失败不能导致隐藏正文或无限等待 |
| 用户向上阅读 | 新文字不强迫跳回底部；恢复跟随后能看见最新完整文字 |

应分别记录句界准确性、边界修订次数、文字上屏延迟、已显示内容重排幅度、处理耗时与资源使用。原型验证可对既有文字事件做本机离线回放，不需要再次采集或上传课堂录音。原生分句探针已执行，流式原型、双语布局比较和神经句界模型性能测试尚未执行；本报告没有将这些未完成的工作计为通过。
